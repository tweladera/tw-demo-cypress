## Ambiguities in Original Acceptance Criteria

These are open questions that must be answered before implementing the missing tests:

1. **Leave balance for Admin users** — The current test suite uses the Admin account which has no leave entitlements in the OrangeHRM demo. Tests that need to submit an actual leave request require either an ESS user account or a way to assign leave entitlements to the test Admin.
   > **Question:** Is there a secondary test account (ESS role, with leave balance) available for E2E tests? Should it be added to the `.env` file?

2. **Leave date validation rules** — It is unclear whether OrangeHRM rejects past dates, weekends, or public holidays at the API level or only at the UI level.
   > **Question:** What is the exact business rule for invalid leave dates in the demo environment?

3. **Session timeout duration** — The demo site's session expiry time is unknown. Tests for session expiry may require artificial time manipulation or a way to invalidate the session via API.
   > **Question:** What is the configured session timeout for the OrangeHRM demo environment?

4. **Pokemon API scope** — `pokemon-api.cy.js` tests an external API (PokéAPI) that is unrelated to OrangeHRM. The intent of mixing HR management E2E tests with Pokémon API tests is unclear.
   > **Question:** Should Pokemon API tests be separated into their own test suite or removed from the OrangeHRM project?

5. **Employee deletion behavior** — It is unclear whether the OrangeHRM demo allows employee deletion or whether it is disabled to protect shared demo data.
   > **Question:** Can the demo's Admin account delete employees, or is this restricted?

6. **Admin Add User — actual save** — The existing `PIM.cy.js` explicitly states it won't save the form "to avoid modifying the demo site data". The same concern applies to Admin Add User.
   > **Question:** Should E2E tests that mutate data use API teardown (delete via API after test), or is there a dedicated test environment where mutations are acceptable?
